# 検討して見送った案と、方針を変えた経緯

> 実装に必要な仕様は`PLAN.md`にあります。この文書は「なぜそうしたか」の記録です。
> 節番号(6.3など)はPLAN.mdの節、「フェーズN」は`docs/phases.md`のフェーズを指します。

## 見送った案

### `github.com/miekg/dns`(DNSのTTL取得)
- `github.com/miekg/dns` はTTL取得のために検討したが、精度向上が小さいことと、後継版(`codeberg.org/miekg/dns`)への移行期であることから見送った
- TTLが効くのは主にFast Fluxの検知だが、「向き先IPの件数と管理組織の分散」(6.5の`fast_flux`)で大部分を代替できる。また、リゾルバ経由で得られるTTLはキャッシュの残り時間で、正確な値ではない
- DNSの取得はインターフェースの裏に置いてあるため(6.2)、必要になれば後から差し替えられる

### 向き先IPのAS番号の取得(Team CymruのDNS照会など)
- 当初は`fast_flux`を「3つ以上のAS番号にまたがる」と定義し、AS番号は向き先IPのRDAPから取る予定だった
- しかし計画時のレビューで実際に照会したところ、IPのRDAP応答には経路のAS番号が基本的に含まれなかった(ARINは拡張項目`arin_originas0_originautnums`があるが空配列、RIPE NCC・APNICは項目なし)
- AS番号を得るにはTeam CymruのIP→ASのDNS照会などの第三者サービスが必要になり、「第三者のサービスに依存しない」方針(6.1)と、外部に渡る情報(READMEの表)に関わるため見送った
- 代わりに、`fast_flux`の分散を**RDAPの管理組織(取れなければネットワークの`handle`)の数**で数える定義に改めた(6.2、6.5)。ルールIDは変えていない

### 同形異字(IDN)の判定とconfusables表
- 実装前の調査(`docs/research/phase0.md`)で、フィッシングURL 8,282件のうちIDNが0件だったため、今回は実装しない。フェーズ5以降に必要性を再判断する
- 将来実装する場合の方針:
  - `golang.org/x/text`にはUnicodeのconfusables(紛らわしい文字)の表がないため、**Unicodeの`confusables.txt`から必要な文字(主にキリル文字・ギリシャ文字とラテン文字の対応)を抜き出して自前で同梱する**。依存の追加は不要
  - 同梱する場合は、表の出典とバージョン、および**Unicode License v3の表記**を、同梱ファイルの先頭とREADMEに記載する
  - 判定の方法は6.3の「判定ルール」の表の「同形異字」の行にある

### その他(3章の「対象外」にも記載)
- 外部の解析サービス(VirusTotal等)、有料の履歴データ:商用利用の制限と、外部への開示のため
- .jp以外のWHOISフォールバック:`.co`・`.me`・`.cn`のWHOISフォールバックは**今回は追加しない**。.jpと同じ仕組み(6.1)で後から追加できるため、フェーズ5で「信頼度:低」の対象の見逃しが問題になれば検討する(件数と見逃しの記録は、フェーズ5の作業項目にしてある)。それまではCTログ(既定の`--ct always`。`auto`でも登録日が取れない対象は照会する)が代わりの根拠になる
- 一括登録の検出:将来の拡張候補。フェーズ5の後に追加を検討する第一候補とした(下記「計画の有用性の見直しで直した点」)
- 自社ブランドの監視、crt.sh以外のCT検索サービス:将来の拡張候補

## 方針を変えた経緯

### CTログの照会の既定を`auto`から`always`に変えた(6.4)
- 当初は「登録日が取れればCTの上乗せはほとんどない」と考え、登録日が取れないときだけ照会する`auto`を既定にしていた
- しかし2.1の測定で、**登録から長く寝かせたドメインを、使う直前に初めて証明書を取って使う**例が見つかった。この層は登録日が古いため「新しさ」の点数が小さく、CTの「使い始め」の手がかりが最も効く。そこで**既定を`always`に改めた**
- 一方でcrt.shの照会は約半数が失敗したため、照会失敗は既定で警告扱いとし、信頼度にも影響させない

### 「新しさ」と「ブランド偽装」を中心の根拠から外した(2.1、6.5)
- 当初は「新規に取得された偽装ドメイン」を主な対象と考えていた
- 調査の結果、登録から30日以内のフィッシングは約1割、ホスト名にブランド名を含むのは登録ドメイン単位で約16%にとどまった
- そのため「ランダム文字列」と「悪用の多いTLD」を重視し、「登録から31〜365日」を加え、「登録から5年以上」の減点を弱めた。変更の一覧はPLAN.mdの2.1にある

### ランダム文字列の判定方法を定めた(6.3)
- 当初の簡易判定(数字を含むだけでも該当)は正常側の該当が約10%と多かったため、正常側との比較で最も該当が少なかった方法(B')に改めた
- 2.1の数字と実装を一致させるため、判定の定義を固定し、参照実装(`tools/eval/phase0/randomcheck.py`)と突き合わせるテストを置く

### 計画時のレビューで直した点(2026年11月11日)
別のセッションでのレビューの指摘を受け、実装前に次の点を直した。
- **ランダム文字列とIDN(6.3)**:参照実装は、Unicodeの`ドコモ-kvqlv`を該当、同じラベルのPunycode`xn---kvqlv-2r4e9f0i`を非該当としていた。2.1の測定はPunycode側(CrUXはPunycode、フィッシング側はIDNが0件)で行ったため、**ASCII以外を含むラベルは全体を判定しない**定義に改め、参照実装も同じに直した。測定データにはASCII以外を含むラベルが無いため、2.1の数字は変わらない
- **`--as-of`を2つに分けた(7章)**:基準日を固定すると照会時点の状態に依存するルールも評価不可になる作りでは、「すぐ照会したデータ」を後日に同じ基準日で採点し直せなかった。そのため`--as-of`(基準日)と`--ignore-current-state`(照会時点の状態を使わない)に分け、`--cache-dir`指定時はDNSも保存し、有効期間で消さないようにした(6.1)
- **CTの照会結果が一部だけの場合(6.4)**:片方の照会の失敗、`--ct-apex-only`、件数・サイズの上限による打ち切りで、見落としの危険は同じため扱いをそろえた。`recent_cert`は一部の結果で該当すれば該当、該当しなければ判断しない
- **別ブランドとの取り違え(6.3)**:`paypal`と`paypay`のように距離の近いブランドで、公式ドメインや別ブランド名がタイポと判定されないようにした
- **相手が決められる値の扱い(11章)**:text出力の制御文字の除去、CSVの数式実行の防止、応答サイズの上限、リダイレクト先を`https`に限ることを加えた

### 計画時の2回目のレビューで直した点(2026年11月11日)
- **公式ドメインの除外の範囲(6.3)**:前回、`paypay.ne.jp`の誤検知を防ぐために「いずれかのブランドの公式ドメインなら、すべてのブランドの判定から除外する」としたが、これでは公式ドメインの一覧がブランド判定全体の許可リストになり、利用者がページを作れる公式ドメイン(`sites.google.com`など)での偽装を見逃す。`paypay.ne.jp`の問題は「別ブランドのキーワードに完全一致する単語はタイポ判定に使わない」で解決しているため、全ブランドの除外は`brand_lookalike`に限り、`brand_contains`と`brand_in_path`はそのブランドだけの除外に戻した
- **`--as-of`の日付だけの指定(7章)**:0時と解釈すると、掲載当日の証明書や登録が「基準日より後」として除かれ、最も効く手がかり(直近の証明書)が落ちる。そのため、JSTのその日の終わりと解釈することにした。JSTはJPCERT/CCのリストと.jpのWHOISの日付に合わせた
- **未登録のキャッシュ(6.1)**:検証用に入れた「404を成功した結果として保存する」が通常の利用にも効き、登録直後でRDAPに未反映のドメインが12時間「未登録」のまま残る。案は「`--cache-dir`指定時だけ保存する」と「通常時は短い有効期間にする」の2つだったが、前者を選んだ。同じ実行の中の重複照会は6.4で防がれるため、短期間のキャッシュで減る照会は少なく、有効期間の設定を1つ増やすほどの利点がないため
- **その他**:`fast_flux`を暫定の配点にした(数え方を管理組織に変えたため)。text出力の制御文字の除去を文字単位と明記した。`--raw`は応答をJSONとして読み直してから出力し、正しいJSONでない応答は照会エラーにした

### 計画時の3回目のレビューで直した点(2026年11月11日)
- **`--raw`の制御文字(5.2、11章)**:応答をJSONとして読み直せば生の制御文字は届かないとしていたが、`json.Compact`が拒否するのは文字列の中の0x20未満の文字だけで、DEL・C1(U+009Bなど)・双方向制御文字・不正なUTF-8はそのまま通る(Go 1.27.3で確認)。.jpのWHOISを包む`encoding/json`の出力も、DEL・C1・双方向制御文字はエスケープしない。そのため、整形のあとこれらを`\uXXXX`のエスケープに置き換え、不正なUTF-8は照会エラーにした。JSONでは文字列の外にASCII以外の文字は現れないため、一律に置き換えても値と構造は変わらない
- **`-o json`とCSVの制御文字(11章)**:`--raw`と同じ理由で、`encoding/json`に任せていた通常のJSON出力(JSON Linesを含む)でもDEL・C1・双方向制御文字がそのまま出力されていた。同じ置き換えを通すことにした(値は変わらない)。CSVにも同じ穴があったが、エスケープの書き方がないため、text出力と同じく除去することにした。CSVは人が表計算ソフトで読むための形式で、値を変えずに渡す役目はJSONが持つため。もう1つの案は「CSVは値を変えず、端末に直接出さないよう注記する」だった

### 計画の有用性の見直しで直した点(2026年11月11日)
計画全体を読み直し、「登録情報の要約と通報先は確実に役立つが、スコアの判定が効くかはフェーズ5まで分からない」と整理した。全体は作り直さず、次の5点を直した。仕様(ルール、配点、固定値)は変えていない。
- **検証データの入手の目処を、フェーズ1の前に確かめる**(`docs/phases.md`、12章の6と7):「すぐ照会した悪性データ」と「難しい正常データ」が無いと、`term_le_1y`・`hold`・DNS由来のルールと暫定の配点を検証できない。手に入らないとわかるのがフェーズ5の直前では、スコアの作り込みを減らす判断が間に合わないため
- **要約と通報先を、判定より先に使えるようにした**(`docs/phases.md`のフェーズ2・3):通報先の表示はフェーズ3の`check`で初めて出る順序だった。判定が外れても価値が残る部分のため、フェーズ2で`check`に要約と通報先を表示し、フェーズ3で判定を加える順序に改めた。できあがるものは変わらない
- **`--ct`の既定`always`を暫定にした**(5.3、6.4):単体の`check`でも毎回crt.shを待つ(2.1の測定で1件あたり約30秒、約半数が失敗)一方で、得られるのは+1〜+2点の根拠で、`always`に変えた根拠も18件の測定だった。フェーズ5の`always`と`auto`の比較と待ち時間の記録をもとに、既定を決め直す。CTを待たずにほかの欄を先に表示する案も、そのときに判断する
- **一括登録のまとめ表示を、フェーズ5の後の第一候補にした**(3章):追加の照会なしで実現でき、ランダム文字列の判定で拾えない一括登録のドメイン(`ockvv.info`、`hsije.info`)を補えるため。追加するかは、フェーズ5で記録する件数を見て相談して決める
- **RDAP非対応のccTLDの再確認を、フェーズ5の作業項目にした**:`.co`・`.me`・`.cn`はURL単位で約12%を占め、「信頼度:低」になる(`docs/research/phase0.md`)。見送りの判断を「問題になれば検討する」のままにせず、件数と見逃しを記録して再確認する
- **判定を主機能から外す基準を、先に決めた**(`docs/phases.md`のフェーズ5、12章の10):スコアが正常と悪性を区別できないとわかった場合に、判定を主機能から外して要約と通報先に絞れるようにするため。結果を見てから基準を決めると判断が甘くなるので、決め方と基準を先に置いた。基準を満たさない場合の対応は自動では決めず、相談する
- **基準を、絶対値から「単純なルールとの比較」に改めた**(同上):最初は目安として「再現率50%以上、誤検知率は上位サイトで5%以下・難しい正常データで30%以下」を置いたが、実データの裏付けが無かった。見直すと、「登録から365日以内なら陽性」という1行のルールだけで悪性の約68%(フェーズ0の37件中25件)を拾える見込みがあり、再現率50%はそれより低い基準だった。そのため、再現率と難しい正常データでの誤検知率は数値を置かず、単純なルールより良いこと(基準A)に改めた。上位サイトでの5%以下(基準B)は、文字列だけの測定(`docs/research/string-score.md`。3点以上が2.8〜3.3%)を根拠に残した
- **配点と基準の調整は、公開後も続ける前提にした**(`docs/phases.md`のフェーズ5「公開後の調整」):実際に届くものの割合や、許せる無駄な確認の件数は、使い始めてからでないと分からないため。運用での誤検知の基準(基準C)は公開後の記録で測る
- **記録を集める仕組みは、ツールに入れない**(同上):案は「判断を入力するコマンドや履歴の保存を本体に持たせる」と「JSON出力を利用者が保存し、`tools/eval/`のスクリプトで集計する」の2つで、後者を選んだ。調べたドメインの一覧は外に出したくない情報で(キャッシュを`0700`・`0600`で作るのと同じ理由)、履歴の管理は「調べたいものを調べる」CLIの範囲を超えるため。配点・閾値は設定ファイル(6.7)で変えられるので、本体に仕組みを足さなくても調整できる
- **文字列だけの点数を、実装前に測った**(`docs/research/string-score.md`):通信なしで評価できるルールだけで、悪性の約27%が「要確認」に届き(正常側は0.3〜0.6%)、約28%は0点だった。`keyword`(ホスト名)と`brand_lookalike`は、仮のブランドリストでは正常側との差が無かった。配点は変えていない(フェーズ5で、通信が必要なルールと合わせて決め直す)

## その他の決定

| 決定 | 理由 |
|---|---|
| 言語はGo、依存は`golang.org/x/net`のみ(4.1) | 単一バイナリで配布でき、個人開発で外部パッケージの保守を追う手間を減らすため |
| 第三者のRDAPサービス(rdap.org等)に依存しない(6.1) | IANAのbootstrapで権威サーバーを直接決められるため |
| `--connect`(対象ホストへの直接接続)は既定でoff(5.3) | 攻撃者側に調査を察知される、悪性サーバーに接触する危険を避けるため |
| 名称は`domtriage`(リポジトリ情報) | RDAP以外の情報も使う不審ドメインの一次判定ツールのため。`domcheck`、`rdapcheck`は既存のツールと重なっていた |
| ライセンスはMIT(リポジトリ情報) | 組織内でも導入しやすく、依存(BSD 3条項)とも組み合わせやすいため |
| 日本語と英語に最初から対応(6.6) | GitHubで公開するため。後から多言語化すると表示処理の作り直しになるため |
