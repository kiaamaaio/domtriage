# 実装フェーズ

> PLAN.mdの「9. 実装フェーズ」を移したものです。移したあとに、計画時のレビューの指摘で作業項目と完了条件を直しています(経緯は`docs/decisions.md`)。
> 本文中の節番号(6.3、2.1など)はPLAN.mdの節を指します。


各フェーズの完了条件を満たしてから次に進むこと。

**進め方の方針**:フェーズ1〜4は、検証(フェーズ5)で必要な機能を優先し、表示の細部などの作り込みは最小限にとどめる。配点や機能は検証結果で変わり得るため、検証より前に作り込みすぎないこと。

| フェーズ | 内容 |
|---|---|
| 0 | **実データの事前調査**(計画時に実施済み。2.1参照) |
| 1 | RDAPの基盤(.jpのWHOISフォールバック、多言語の基盤を含む) |
| 2 | DNSとCTログ |
| 3 | 文字列判定とスコアリング |
| 4 | 一括処理(検証に必要な部分) |
| 5 | **実データでの検証と調整** |
| 6 | 出力形式と仕上げ |

## フェーズ1:RDAPの基盤
- 引数の並べ替え処理とサブコマンドの骨組み
- **多言語対応の基盤**(言語の判定、メッセージカタログ、フォールバック)。以降のフェーズの表示文字列はすべてカタログ経由で追加する(英語の翻訳はフェーズ6。6.6参照)
- 入力の正規化(eTLD+1のICANN/private判定、IDN)
- 入力の受け付け(URL・無害化表記からのホスト名の取り出し。6.0参照)
- bootstrapの取得とキャッシュ。**主要ccTLDの対応状況を確認して記録**
- ドメイン・IP・AS番号の照会、リダイレクト、429の再試行
- レジストリ→レジストラの2段階照会と統合
- **.jpのWHOISフォールバック**(6.1参照。実装前にJPRSのWHOISの利用条件を確認し、内容を報告する)。**利用条件の確認待ちで止まらないよう、フェーズ1の中で最後に着手する**
- RDAPのモデル定義とjCardパーサー、伏せ字の判定
- `domtriage domain` / `ip` / `asn` のtext出力と `--raw`、終了コード

**完了条件**
- `domtriage domain example.com`、`domtriage ip 8.8.8.8`、`domtriage asn 15169` が要約を表示する
- `domtriage domain example.com -o json` のように、オプションを後ろに書いても動く
- `user.github.io`を渡すと`github.io`で照会し、共有ホスティング上のサイトと表示する
- `domain`でRDAP非対応TLDを指定すると、「このTLDはRDAPに対応していません」と表示して終了コード3で終わる(異常終了しない。PLAN.md 5.4)
- `.jp`(`co.jp`等の属性型を含む)のドメインで、WHOISから登録日・有効期限・状態が取得・表示される
- bootstrapに`.jp`が載っている場合(フィクスチャで再現)は、WHOISではなくRDAPが使われる
- `https://example.com/login?x=1`、`hxxps://example[.]com`、`example.com:8443/x`(スキームなし、ポート付き)を渡すと`example.com`として扱われる
- `co.jp`(ICANNのサフィックスそのもの)は不正な入力になり、`github.io`(privateサフィックスそのもの)は通常のドメインとして扱われる
- `http://192.0.2.1/login`は「対象外」となり、エラー(終了コード3)にならない
- `domain`に`http://192.0.2.1/login`を単体で渡すと終了コード2で`ip`コマンドを案内し、一括処理では「対象外」となって終了コード3・4にならない
- 言語の優先順位(`--lang` > `DOMTRIAGE_LANG` > 設定ファイル > `LC_ALL`等)どおりに表示言語が決まり、ヘルプと引数エラーも選んだ言語で表示される(ヘルプとエラーの英語はフェーズ1で揃える。6.6参照)
- .jpのWHOISで未登録のドメインが、`domain`では終了コード4になる
- 制御文字(ANSIエスケープ)や双方向制御文字を含むレジストラ名・登録者名が、除去されてtext出力に表示される。日本語を含む値は壊れず、不正なUTF-8のバイト列は置換文字になる(PLAN.md 11章)
- 文字列の中に生の制御文字(C0)を含むRDAP応答(規格に反するもの)と、不正なUTF-8のバイト列を含む応答は、`--raw`で出力されず照会エラーになる。DEL・C1(U+009B等)・双方向制御文字(U+202E等)を含む応答は、それらが`\u009b`のようなエスケープに置き換えられて出力され、生のまま出力されない。.jpのWHOISを包んだJSONと、`-o json`(JSON Linesを含む)の出力も同じ。正しい応答は、キーの順番と値を変えずに出力される(PLAN.md 5.2、11章)
- RDAPのリダイレクト先が`https`以外の場合は追従せず、読み込みサイズの上限を超える応答は照会エラーになる(PLAN.md 11章)
- フィクスチャを使った単体テストが通る(ネットワークなし)

## フェーズ2:DNSとCTログ
- DNSレコードの取得、向き先IPのRDAP照会、向き先の分散(件数・管理組織の数・国数)の集計(AS番号は取得しない。PLAN.md 6.2)
- crt.shの2回照会、重複除去、「取得失敗」と「0件」の区別
- `--connect` によるTLS証明書取得

**完了条件**
- DNS・CTの結果が取得でき、crt.shが落ちていても処理全体が止まらない
- 事前証明書と本番証明書が重複して数えられない(フィクスチャで確認)
- DNSとCTログが6.0の表どおりの名前に照会する(サブドメイン付きの入力と`user.github.io`で確認)
- 向き先IPのRDAPから、ホスティング事業者の管理組織とabuse連絡先を取得できる(表示はフェーズ3の`check`で行う)
- ARIN・RIPE NCC・APNICの応答のフィクスチャで、管理組織が取り出せ、向き先の分散(管理組織の数・国数)が数えられる。ARINで国が取れない場合は「不明」になり、国の数に含まれない
- crt.shの応答が件数・サイズの上限を超える場合に、逐次読みで打ち切られ、「照会結果が一部だけ」として扱われる(フィクスチャで確認)
- `--connect` なしでは対象ホストに一切接続しない(テストで確認)
- **実際のリゾルバでの確認**(結合テスト。`//go:build integration`):Linux(WSLを含む)とWindowsのそれぞれで、次の3種類を引き、正しく区別できる。モックのテストでは見つからない問題のため、実環境で確かめる
  - 存在するがMXの無いドメイン → 存在すると判断され、`no_mx_spf`が評価される
  - 存在しないドメイン → `no_mx_spf`と`fast_flux`が評価不可になる
  - 登録ドメインは存在するが、サブドメインが存在しないホスト → `fast_flux`だけが評価不可になる
  - 使うドメインは、結果が変わりにくいもの(例:IANAの予約ドメインの配下で存在しない名前)を選び、テストに記載する

## フェーズ3:文字列判定とスコアリング
- 文字列判定の各ルール(単語ごとの比較、長さによるルール、ランダム文字列、悪用の多いホスティング・TLD、URLのパス)
  - 2.1の結果に従い、**ランダム文字列の判定に手をかけ**、ブランド偽装の精巧さ(同形異字など)には手をかけすぎない
- 設定ファイル(6.7)の読み込み・既定値(`default_config.json`)との統合・検証
- `Signal` の生成、グループ上限、点数合算、信頼度、判定理由の表示
- `domtriage check`

**完了条件**
- 公式ドメイン(ブランドの `official_domains`)とそのサブドメインが偽装判定されない
- `paypal.com.secure-login.xyz`のようにサブドメインに仕込まれた偽装を検出する
- 短いキーワードで誤検知しない(`sauna`、`banana`、`online`、`airline`などが一致しない)
- `exclude_words`に登録した語が一致しない
- `https://example.pages.dev/paypal/login`で、パスのブランド名(`brand_in_path`)と不審キーワード(`path_keyword`)、無料ホスティング(`abused_hosting`)が検出される
- 公式ドメイン上のURL(例:`https://www.paypal.com/signin`)では、パスのブランド名が加点されない
- 別のブランドの公式ドメイン上のURLでは、パスのブランド名が除外されない(例:Googleの公式ドメインに`google.com`を含むブランドリストで、`https://sites.google.com/view/paypal-login`がPayPalの`brand_in_path`として検出される)。全ブランドからの除外は`brand_lookalike`だけに効く(PLAN.md 6.3「公式ドメインの除外」)
- ドメインだけの入力では、パスのルールが評価不可ではなく「該当なし」になる
- `user.github.io`がGitHubの偽装と判定されず、`paypal-login.github.io`は`paypal`の偽装として検出される
- privateサフィックス上のサイトで、RDAP由来のルールと「MXもSPFもない」が評価不可になり、証明書0件のときは初回証明書のルールも評価不可になる
- タイポ・文字置換の代表例がテーブルテストで検出される
- ランダムらしい登録ドメイン(例:`yqspzy.com`、`jgfjfjfg.cc`、`kvqlv.info`)が`random_label`で、サブドメイン(例:`cj49xv9v.example.com`)が`random_subdomain`で検出される
- 6.3の「判定の例」の表と「既知の誤検知」がすべて期待どおりになり、参照実装(`randomcheck.py`)と同じ結果になる
- **検出しない例**:普通の英単語の組み合わせ(`drawboardhq.com`)、子音の多い正規の略語(`smbc`、`kddi`、`mufg`、`jcb`、`nhk`、`ntt`)、ハイフンを含む普通の語(`x-trend`)、Punycodeのラベル(`xn--`で始まるもの)
- ブランド偽装が該当したとき、`official_domains`への追加の案内が表示される
- `paypal`と`paypay`の両方を含むブランドリストで、`paypay-login.xyz`がPayPalのタイポと判定されず、`paypay.ne.jp`がどのブランドの偽装とも判定されない
- 「通報先」欄に、レジストラとホスティング事業者のabuse連絡先が並んで表示される
- 既定(`--ct always`)ではcrt.shに照会する。`--ct auto`で登録日が取れた対象では照会せず、CT由来のルールが「省略」になる。設定ファイルの`"ct": "never"`で既定を変えられる
- `abused_tld_high`(例:`.top`)と`abused_tld_moderate`(例:`.info`)がそれぞれの配点で該当する
- 設定ファイルで既定と別の段階に書いたTLD(例:`info`を`high`に)は、書いた段階だけで該当する。利用者の設定で`high`と`moderate`の両方に同じTLDを書くと終了コード2になる
- 不審キーワードは、異なるキーワードを2個までしか数えない
- 6.5の想定例(`kvqlv.info`、登録から約285日、初回証明書が7日以内)が「高」に、CTの照会に失敗した場合でも「要確認」になる
- 正規の新規ドメインを想定した入力(新しさのみ該当)が「要確認」止まりになる
- 登録から約300日で、ランダムらしい名前のドメイン(6.5の想定例)が「要確認」以上になる
- 登録から5年以上のドメインの減点が-1になる
- 判定理由がすべて表示され、評価不可・省略のルールと信頼度が正しく表示される
- RDAP非対応TLD、privateサフィックス、RDAPの404の各ケースで「信頼度:低」になり、`--ct never`だけでは信頼度が下がらない
- RDAPの照会失敗(タイムアウト等)は終了コード3の対象になり、RDAP非対応TLD・privateサフィックス・404は対象にならない
- `--fail-on-low-confidence`指定時、信頼度が低く判定が「低」の対象で終了コード1になる
- `check`で`--raw`を指定すると終了コード2になる
- 設定ファイルで一部の項目だけを書いた場合に、残りが既定値のまま使われる
- 設定ファイルの誤り(未知のキー、未知のルールID、`review >= high`など)で終了コード2になる
- `.jp`のドメインで、WHOISから登録日が取れれば「信頼度:低」にならない
- 既定ではCTログの照会失敗だけでは終了コード3にならず、CT由来のルールが評価不可になり、信頼度は下がらない(`--ct-errors-as-errors`はフェーズ4)
- `--ct-apex-only`指定時に、`cert_lt_7d`が「省略」になり、`recent_cert`は該当した場合だけ評価され、該当しなければ「省略」になる

## フェーズ4:一括処理
フェーズ5の検証で大量の対象を流すために必要な部分を先に作る。
- ファイル・標準入力からの読み込み(URL・無害化表記を含む)、同時実行数の制御
- **ホストごとの同時接続数の制限**(上限はPLAN.md 11章)
- `Retry-After`の上限(60秒)の適用
- JSON / JSON Lines 出力
- 終了コードの優先順位、`--ct-errors-as-errors`
- 検証用の隠しオプション`--as-of`・`--ignore-current-state`(7章「日付の表示」)、`--cache-dir`・`--cache-only`(6.1)
- 同じ実行の中での重複照会の防止(6.4)

**完了条件**
- 100件程度のリストを処理して、レート制限で失敗が連鎖しない
- 不正な行を含むリストでも処理が最後まで進み、その行だけがエラーになる
- 同じホストへの同時接続数が上限を超えない(テストで確認)
- 同じ登録ドメインを含む行が多数あるリストで、RDAP・CTの照会が登録ドメインごとに1回になる(テストで確認)
- `--as-of`指定時に次のとおり動く(フィクスチャで確認)
  - 基準日より後に発行された証明書は、初回・直近の証明書の判定に使われない
  - 登録日が基準日より後のドメインでは、登録日由来のルールが評価不可になり、信頼度が低になる
  - `term_le_1y`、`hold`、`no_mx_spf`、`fast_flux`は評価される(`--ignore-current-state`なし)
  - 日付だけの指定(`--as-of 2026-09-15`)は`2026-09-15T23:59:59.999999999+09:00`と解釈され、その日(JST)に発行された証明書と、その日に登録されたドメインの登録日が基準日以前として扱われる。実行環境の時刻帯(`TZ`)を変えても結果が変わらない
- `--as-of`と`--ignore-current-state`を指定すると、`term_le_1y`、`hold`、`no_mx_spf`、`fast_flux`が評価不可になる。`--ignore-current-state`だけを指定すると終了コード2になる
- `--ct-errors-as-errors`指定時は、CTログの照会失敗で終了コード3になる
- 登録ドメインのNSが引けないドメインで`no_mx_spf`が、ホスト名のA/AAAAが引けない対象で`fast_flux`が評価不可になり、終了コード3にならない(通常の判定でも)。サブドメインだけが存在しない場合は`fast_flux`だけが評価不可になる
- `--cache-dir`で照会した結果を`--cache-only`で2回採点すると、DNS由来のルールを含めて同じ結果になる。キャッシュに無いものは照会されず、該当するルールが評価不可になる
- `--cache-dir`指定時は、有効期間を過ぎたキャッシュも削除・照会し直しされない(現在時刻を進めたテストで確認)
- `--cache-dir`指定時は、RDAPの404と.jpのWHOISの「該当なし」が保存され、`--cache-only`での採点し直しでも「未登録」になる
- 通常のキャッシュ(`--cache-dir`なし)では、404と「該当なし」が保存されず、次の実行で照会し直される(PLAN.md 6.1)
- crt.shの2回の照会のうち片方だけ失敗した場合に、`cert_lt_7d`は評価不可になり、`recent_cert`は成功した側で該当すれば該当、該当しなければ評価不可になる
- crt.shの5xx・タイムアウトで1回だけ再試行し、失敗した照会と理由が`errors`に記録される

## フェーズ5:実データでの検証と調整

配点・閾値は設計上の仮の値なので、**作り込む前に実データで検証し、調整する**。

**検証用データ**
- **2種類の悪性データを、用途を分けて使う**

| データ | 照会までの日数 | 用途 |
|---|---|---|
| **すぐ照会したデータ**:自組織に届いた通報など、届いた日にその場で照会して保存したもの(集め方は実装時に相談。12章) | 数日以内 | `--as-of <最初に照会した日>`で、全ルールを評価する(`--ignore-current-state`なし)。`term_le_1y`・`hold`・DNS由来のルールの効き方は、このデータでしか測れない |
| **JPCERT/CCのリスト**(GitHubの`phishurl-list`) | 2週間以上(下記) | `--as-of <リストに載った日> --ignore-current-state`で評価する。照会時点の状態に左右されるルールは評価不可になる |

- JPCERT/CCのリストは、月ごとのファイルが月末からしばらく後に公開される(計画時点の2026年11月9日に、10月分はまだ公開されておらず、9月分は10月16日ごろの更新に含まれていた)。そのため**掲載から照会まで最短でも2週間以上かかり、「すぐ照会したデータ」の代わりにはならない**
- 悪性の例(JPCERT/CCのリスト)の扱い:
  - **リストの日付が取得日からN日以内のエントリだけを使い、取得後できるだけ早く照会する**。古いエントリは、照会時点で既にドメインが削除されていることがある。特に**ブランド名を含むドメインは早く削除される**傾向があり(2.1)、照会が遅れるとブランド偽装のルールが実際より効かないように見えてしまう
  - 登録日はドメインを取り直さない限り変わらないため、「登録からの日数」は**リストに載った日を基準に**計算する(照会日ではなく)
  - リストは毎日更新されるとは限らないため、Nは固定せず、実データの件数を見て決める(極端に件数が少なければ相談する)
  - 各エントリについて、**リストでの確認日から照会日までの経過日数**を記録する(新しさのルールの効き方に直結するため)
  - **公開された最新月のリストから取り、公開後できるだけ早く照会する**。2.1の37件のうち14件は2025年10〜11月の登録で、計画時点でちょうど1年の期限を迎えていた。更新されなかったドメインは猶予期間を経て数か月以内に削除されるため、照会が遅れるほど評価できるデータが減る
  - 照会は最初の1回だけ行い、結果を`--cache-dir`に固定する。以降の採点し直しは`--cache-only`で行う(6.1)
  - 照会時点で404(未登録)だったものは、照会エラーと同じく集計から分け、件数だけ記録する
- 正常な例:
  - Trancoなどの上位サイトのリスト
  - **最近登録された正規のドメイン**(正規の新規サイトが「高」にならないかを確かめるため。集め方は実装時に相談する)
  - **パス付きの正規のURL**(例:正規サイトのログイン画面`https://www.example.com/login`)。`brand_in_path`・`path_keyword`の誤検知を測るため
  - **無料ホスティング上の正規のサイト**(`abused_hosting`の一覧にあるサフィックス上の正規のサイト)。`abused_hosting`の誤検知を測るため
  - **悪用の多いTLD上の正規のサイト**。`abused_tld_high`・`abused_tld_moderate`の誤検知を測るため
  - **通報されたが正規だったもの**:正規企業のキャンペーン用ドメイン、メール配信サービスのクリック計測用ドメインなど。利用者が実際に不審に思って回してくる「難しい正常データ」で、ブランド偽装のルールの誤検知を測るため
  - 「パス付きの正規のURL」と「無料ホスティング上の正規のサイト」が無いと、暫定配点のルールが正常データでほとんど発火せず、誤検知を測れない。集め方は実装時に相談する(12章)
- 件数は各100〜200件程度を目安とし、照会先に負荷をかけない(`--ct-apex-only`の利用も可。ただし`cert_lt_7d`が「省略」になり、`recent_cert`も該当しない場合は「省略」になるため、これらのルールの効き方を測るデータには使わない)
- 検証時点での.jp・gTLD・その他ccTLDの内訳も記録する

**検証の方法**
- 検証用のスクリプトは`tools/eval/`に置く(ツール本体には含めない)。本体のバイナリを`-f -o json --as-of <基準日> [--ignore-current-state] --cache-dir <検証用> [--cache-only]`で呼び出して集計する(採点の処理を検証側に二重に持たない)
  - `--as-of`は1回の実行で1つの値のため、基準日(リストに載った日、または最初に照会した日)ごとに対象を分けて呼び出す。日付だけを渡すとJSTのその日の終わりと解釈される(PLAN.md 7章「日付の表示」)
  - すぐ照会したデータは、最初に照会した日時を対象ごとに記録しておく。呼び出しは照会した日(JST)ごとにまとめてよい(PLAN.md 7章)
- 判定(低/要確認/高)ごとの件数、「要確認以上」を陽性とした場合の**適合率と再現率**、ルールごとの発火率を集計する
- 適合率は悪性と正常の件数の比率で大きく変わるため、**検証データの比率を明記**し、あわせて実際の運用に近い比率(大半が正常、例:悪性1:正常99)を仮定した場合の適合率も算出する
- 「対象外」(ホストがIPアドレス)、照会エラー、照会時点で404のものは集計から分け、件数だけ記録する
- `--ignore-current-state`で評価不可になるルール(`term_le_1y`、`hold`、DNS由来)の効き方は、「すぐ照会したデータ」で別に集計する
- 誤検知・見逃しの代表例を記録する
- 結果は`docs/evaluation.md`にまとめる(実施日、データの出典と取得日、件数、結果、調整内容)
- 検証用のデータそのものはリポジトリに含めない(出典と取得方法のみ記載する)

**調整**
- 結果をもとに、配点・グループ上限・閾値の既定値を見直す。特に**暫定の配点**(`age_31_365d`、`recent_cert`、`random_label`、`random_subdomain`、`age_ge_5y`、`brand_in_path`、`path_keyword`、`abused_hosting`、`abused_tld_high`、`abused_tld_moderate`、`fast_flux`)は必ず検証結果で決め直す。`fast_flux`は配点に加えて「5件以上」「3つ以上の管理組織」の条件も確認する(PLAN.md 6.5)
- 「登録からの日数」の分布を、2.1の40件より大きなデータで測り直す
- crt.shの照会失敗の内訳(どちらの照会が、どの理由で失敗したか)と、再試行による取得率の改善を記録する
- `recent_cert`の正常側の該当率には**測定時期を必ず添える**(証明書の有効期間の短縮で年々変わるため)
- `--ct always`と`--ct auto`の比較(6.4)を行い、判定が変わる件数と処理時間を記録する
- `recent_cert`と`random_subdomain`の**正常側の該当率**を測る(2.1では未測定、または過小評価の可能性がある)
- `term_le_1y`と`age_31_365d`の重なり(6.5の注意)を確認する
- 英数字混在のランダム判定(2.1の方法C)を追加する価値があるかを判断する
- 同形異字の判定(今回は対象外)を追加する必要があるかを判断する
- **`cert_lt_7d`の定義の見直し候補**:前の所有者の証明書があると「初回」が古くなり、取り直したドメインを拾えない(2.1に例あり)。「現在の登録日以降で最初の証明書」と定義し直す価値があるかを判断する(ルールの定義の変更のため、採る場合は相談する)
- **privateサフィックス上のランダムな名前**(例:S3のランダムなバケット名)は、`random_subdomain`(+2)と`abused_hosting`(+1)で3点止まりで、個別の証明書も無いことが多いため、パスに特徴がなければ「低(情報不足)」になる。これが意図どおりでよいかを確認する
- 正規の無料ホスティング上のフィッシングと、意味のない文字列のドメインに対する再現率を、それぞれ分けて記録する(既知の弱点がどの程度か把握するため)
- 機能の追加や削除が必要と判断した場合は、**実装前に相談する**

**完了条件**
- `docs/evaluation.md`があり、調整前後の結果と調整の根拠が記録されている
- 調整後の既定値で、フェーズ3の完了条件(テスト)が引き続き通る(テストの期待値を変える場合は理由を記録する)

### READMEに必ず含める内容
- **冒頭にツールの位置づけを明記する**。主機能は次の2つとして打ち出す
  1. **一次判定**:調査対象を**共有型の解析サービス(VirusTotal、urlscan.io等)に提出せずに**、登録から1年以内、または意味のない文字列の不審ドメインをふるい分ける
  2. **通報先の特定**:レジストラとホスティング事業者のabuse連絡先をまとめて表示し、テイクダウン依頼などの実務を助ける(判定が外れても役に立つ)
  - あわせて「正規のホスティング上のフィッシングや、乗っ取られた古いドメインは検出しにくい場合がある」と書く
- **想定する規模**:既定(`--ct always`)では、crt.shの照会が1件あたり約30秒かかるため**1日数十件程度**を想定する。それ以上(1日数百件程度)を処理する場合は`--ct auto`を使う(キャッシュと重複照会の防止で、実際の照会数はさらに減る)。常時流れるフィードの処理には向かないこと
- **定期的に見直すルール**:`recent_cert`は、証明書の有効期間の短縮(2029年に最長47日)によって正規のサイトでも該当しやすくなっていくため、検証結果の測定時期とあわせて記載し、定期的に見直すこと

- **外部に渡る情報**:「共有型の解析サービスに提出しない」は、どこにも何も渡らないという意味ではない。次の表をREADMEに載せ、正確に説明する
